- `documentation-agent@0.1.0`, a dev agent that takes one `docs` ticket for a merged change (the range or the change in `body`, the changed source in `impacted_paths`) and brings the README, `docs/` and the docstrings up to date. Its answer lists the files written and, for each docs change, what now describes the code and why. Its file policy allows Markdown, `docs/**` and source files; the build loop's docs check then holds the source to docstrings and comments. It runs `claude-sonnet-5-5` at effort `xhigh` behind `action-guard@^0.1`, sandboxed. Its four eval cases (a new function, a new class, a renamed function, a new module) are graded by `sandbox_tests` with a rubric; they, its publish check and its live test have not been run yet (#97).
- `factory build` sends `docs` tickets to the documentation agent and runs a docs check after each round's commit (`pipelines/docs_check.py`): a Python file may change only in its docstrings and comments (compared with `ast`), a file in another known language only in its comment lines, a file of unknown type only if it is a docs file, and a round may not delete any file or create a source file. A breach stops the run before the suite with its own error and escalates the item under the `check_failed` trigger; a Python file that already did not parse at the ticket's ref (`BaseUnparsableError`) leaves it `blocked` instead (#97).
- `factory build --dry-run` writes the change it would have opened as a pull request to `out/<run_id>.patch`, which `git apply` takes at the ticket's ref, and names it in the report's `pull_request.patch` and the text output (#97).
- A `sandbox_tests` eval case may set `expected.run.doc_drift` to the Python files and docs globs the deterministic drift check in `evals/doc_drift.py` reads: every public name needs a docstring and a mention in a docs file, no docs file may name a name gone from the code, and no code may change outside docstrings and comments (#97).
