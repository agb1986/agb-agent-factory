- `triage-diagnostics@0.1.0`, an `sre` agent that reads one saved Sentry issue and the repository at the release the event came from, with read-only tools (`git.read_file`, `rg.search`, `deps.graph`, `deps.impact`), and returns a title, a summary, reproduction steps, the suspected paths from `deps.impact`, the culprit lines, a confidence and a draft reproduction test. Its four eval cases are fixtures with a planted crash and a hand-written event (`crash-empty-average`, `crash-first-of-empty`, `crash-loader-caller`, `crash-missing-config-key`); they, its publish check and its live test have not been run yet (#108).
- `factory incident <repo> --event JSON|@FILE`, which resolves the event's release to a commit, runs triage-diagnostics on a throwaway clone at that commit, runs test-writer unchanged in reproduce mode, runs the test in the offline sandbox and files one `incident` ticket: `ready` with the test attached when it fails the way the event did, `todo` otherwise. The ticket body has a fixed layout (`BODY_SECTIONS`, `incident_sections`, `is_reproduced` in `pipelines/incident.py`) for the hotfix pipeline to read; the guide is `docs/incident.md`. The pipeline never calls Sentry (#108).
- The `incident` eval grader, which checks that the suspected paths name the planted fault and that the reproduction test fails at the release with the event's exception raised from the event's file (#108).
